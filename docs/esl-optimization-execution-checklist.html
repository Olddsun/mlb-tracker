ESL v1 Execution Checklist

ESL 優化執行清單

這份文件是給 Claude Code 執行用的最新版規格：主站搬到 Cloudflare Pages，正式資料搬到 Supabase DB， 三位玩家可在網站上直接提交戰績。第一版不做可編輯確認畫面，玩家只要填「誰用哪一隊」並上傳 5 張任意順序截圖， AI 會先判斷每張圖的角色，再解析資料；硬性驗證通過後直接更新正式戰績。

Cloudflare Pages + Pages Functions Supabase PostgreSQL + Storage Claude Vision AI 單次 call 完成分類 + 解析 無可編輯確認畫面 5 張截圖任意順序 速度優先

最終產品決策

  • 公開戰績網站搬到 Cloudflare Pages。
  • 正式資料搬到 Supabase PostgreSQL，不再以 data/games.json 作為長期資料庫。
  • 截圖存在 Supabase Storage，前端用 signed upload URL 直傳，不經過 Function body。
  • 玩家 token 第一版可等於名字：Scott、Alvin、Vincent。
  • 玩家不需要排序截圖，只需要一次上傳 5 張 box score 圖片。
  • AI 必須在同一次 Vision call 內完成 image role classification 與 box score extraction。
  • AI 解析後不顯示可編輯確認畫面；硬性驗證通過就直接寫入 DB。
  • needsReview 與重複偵測只做提示與 log，不阻擋提交。

第一版刻意不做

  • 不做會員系統。
  • 不做 Scott 審核流程。
  • 不做所有欄位可編輯的確認頁。
  • 不做多聯盟。
  • 不做 NBA 2K schema。

資料欄位補強說明

欄位 / 規則意思為什麼需要
NOT NULL這個欄位不能空白。避免一場比賽缺少比分、玩家、日期，導致戰績算錯。
CHECK限制欄位只能是某些值。例如 home_away 只能是 home 或 away。
UNIQUE不能重複。例如 legacy_id 避免同一場舊資料被遷移兩次。
SV / HLD投手決定欄位的救援成功與中繼成功。目前資料已有 SV、HLD，不能只支援 W、L。
needs_reviewAI 覺得某些欄位不確定。第一版不阻擋提交，只用來事後查錯。
uncertaintiesAI 不確定的具體欄位清單。如果之後要修資料，可以知道是哪裡可能有問題。
duplicate_candidates可能重複的比賽清單。不擋提交，但事後可查是否同一場被送兩次。
request_ip提交者的 IP。token 很簡單時，至少保留基本稽核資訊。
user_agent提交者瀏覽器 / 裝置資訊。方便追蹤問題，例如某台手機壓圖或上傳失敗。
raw_user_input玩家原始輸入，例如「Scott 洋基 / Alvin 道奇」。保留 AI 解析前的原始上下文。
source資料來源，例如 manual_migration、ai_submission。分辨舊資料遷移與新上傳資料。

重點原則

這些欄位不是為了把流程變複雜，而是讓第一版即使「快速直接寫入」，也能保留足夠紀錄，之後真的錯了可以查得到、修得回來。

  check (status in ('received', 'uploaded', 'parsing', 'committed', 'failed')),

Phase 1 Supabase 資料層

  1. 建立 players、teams、games、game_sides、batting_lines、pitching_lines、game_notes、submissions。
  2. 補上 NOT NULL、CHECK、UNIQUE 約束。
  3. 建立 Storage bucket：box-score-submissions。
  4. 先 seed 三位玩家與 MLB team mapping。

Phase 2 舊資料遷移

  1. 寫 scripts/migrate-games-to-supabase.js。
  2. 將現有 8 場從 data/games.json 匯入 Supabase。
  3. 使用 legacy_id 防止重複插入。
  4. 遷移資料的 source 設為 manual_migration。

Phase 3 API 與前端資料來源

  1. 新增 functions/api/games.js，從 Supabase 組回接近原本 games.json 的資料形狀。
  2. js/app.js 只把 fetch('data/games.json') 換成 fetch('/api/games')。
  3. 首頁、對戰列表、隊伍戰績、球員數據、單場詳情必須與舊版一致。

Phase 4 Cloudflare Pages

  1. 接 GitHub repo 到 Cloudflare Pages。
  2. 設定 Cloudflare secrets：SUPABASE_SERVICE_ROLE_KEY、ANTHROPIC_API_KEY、PLAYER_TOKENS。
  3. 在 preview 環境驗證 DB 讀取版。

Phase 5 截圖提交流程

  1. 新增主站「提交戰績紀錄」按鈕。
  2. 提交頁欄位：提交者、token、玩家隊伍對應、5 張任意順序截圖。
  3. /api/create-upload-session：驗 token、建 submission、回傳 signed upload URLs。
  4. 前端壓縮圖片到 max width 1600px、JPEG 0.82，直傳 Supabase Storage。
  5. /api/process-submission：讀圖、呼叫 Claude Vision 一次，在同一次 response 取得 image_roles 與完整 game data，再驗證、寫入 DB。

Phase 6 驗證與警示

  1. 硬性驗證：winner、innings、batting 合計、pitching 失分、IP 格式。
  2. needsReview：只記錄，不阻擋。
  3. duplicate detection：只記錄，不阻擋。
  4. 成功頁顯示比分摘要、winner、提交者、warning 狀態。
  5. 驗證失敗頁顯示具體錯誤、submission ID，並說明截圖已保存或未保存。

AI / Storage 實作注意

  • 圖片直傳 Supabase Storage，不要塞進 Cloudflare Function request body。
  • AI 解析時，Function 用 service role 讀取 private bucket 圖片，或產生短效 signed read URL 傳給 Claude Vision。
  • 不要讓前端拿到 service role key。
  • Claude Vision prompt 要明確說：5 張截圖是任意順序，不可假設第 1 張就是總比分。
  • AI 必須在單次 call 中同時輸出 image_roles 與完整 game，不可先分類 call 一次、再解析 call 一次。
  • 若任何圖片無法辨識為必要 box score 類型，直接回傳 fatal error，submission 設為 failed，不得寫入正式 DB。
  • 玩家隊伍對應是事實，不可改；看不清楚就標記 needsReview，不要編造。

驗收標準

  • 現有 8 場資料完整顯示。
  • 三位玩家任兩人可提交。
  • 5 張截圖任意順序仍可成功解析。
  • AI 單次回傳 image_roles 與 game，並能對應到正確玩家與隊伍。
  • 圖片完全無法辨識時，submission 變成 failed，前端顯示第幾張圖片有問題。
  • token 錯誤不可建立 upload session。
  • 截圖不經過 Function body。
  • 硬性驗證失敗不寫入正式資料。
  • needsReview / duplicate 只做紀錄與提示。
  • API key 與 service role key 不出現在前端。

圖片無法識別時的出口

如果 5 張截圖中任何一張完全無法辨識為 box score，不要硬解析。

{
  "image_roles": [
    {
      "image_id": "img_3",
      "role": "unknown",
      "confidence": 0.12,
      "reason": "圖片不是 box score，或畫面太暗無法辨識"
    }
  ],
  "game": null,
  "needsReview": true,
  "fatalError": true,
  "errorCode": "unrecognized_image",
  "errorMessage": "第 3 張截圖無法辨識為 box score"
}
  • 後端收到 fatalError = true 時，設定 status = failed。
  • 不寫入正式比賽資料。
  • 前端顯示是哪一張圖片有問題。

AI 成功解析，但硬性驗證沒過，也不能黑盒失敗。
