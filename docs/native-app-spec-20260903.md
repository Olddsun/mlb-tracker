## 0. 先處理：現在線上就有的風險

這三件事跟原生 App 無關，是目前 PWA 已經存在的問題。

### 🔴 `/api/delete-game` 完全沒有驗證（最嚴重）

任何人 POST `{"id":"<uuid>"}` 就能永久刪除一場比賽，cascade 掉 game_sides / batting_lines /
pitching_lines / game_notes。而比賽的 UUID 由公開的 `/api/games` 直接回傳。
**實測確認**：用不存在的 UUID 打線上端點，會回「找不到這場比賽」——代表沒有任何身分檢查就進到資料庫查詢。
換成真 ID 就會刪掉。抓一次清單跑迴圈即可清空整個資料庫，沒有備份、無法還原。

### 🟠 `/api/submit-game` 沒有驗證也沒有限流

2026-08-30 拿掉 token 後全開。上架後網址等於公開，任何人都能燒 Anthropic 額度，成本無上限。

### 🟠 比賽日期用 UTC，台灣半夜的比賽會記成前一天

`submit-game.js` 用 `new Date().toISOString().slice(0, 10)`，Cloudflare Workers 跑在 UTC。
台灣 = UTC+8，所以**台灣時間 00:00–08:00 記錄的比賽都會被歸到前一天**。
（討論當下實測：台灣 9/3 00:51，程式會寫入 `played_at = 2026-09-02`。）
新版必須用台灣時區計算日期。

### 其他營運問題
- Supabase 免費方案閒置 7 天自動暫停 → 公開產品必須升級付費（約 US$25/月）。
- `manifest.json` 描述還寫「Scott vs Alvin 的電競對戰聯盟」，已不符現況。

## 1. 產品定位（已定案）

**朋友之間的電玩累積數據記錄。**

## 2. 技術選型（已定案）

### 前端：React Native + Expo（與 ivey 同一套）

選它不是因為技術上最優，是**對 Scott 的處境最優**：

- 已經有跑得動的流程（EAS build、OTA、ASC 上架），不用學新東西。
- **OTA 是關鍵**：前端修正不用送審，「發現 bug 到修好上線」是半小時而非三天。對沒有工程團隊的產品差別巨大。
- 一份程式碼將來可延伸 Android。

已排除的選項：
- **Swift/SwiftUI**：原生體驗最好，但 iOS-only、與 ivey 零共用、**沒有 OTA**，每個小修都要送審。
- **Capacitor 包現有 PWA**：最省事，但正是 Apple Guideline 4.2 會退件的「網頁包殼」，等於繞回原點。

⚠️ **EAS 免費方案每月 30 builds，與 ivey 共用同一額度**，兩個 App 同時開發要注意。

### 什麼能沿用、什麼不能

| 沿用 | 重寫 |
|------|------|
| Supabase schema（含 batting/pitching 結構） | `js/app.js` 全部（vanilla DOM 操作，RN 沒有 DOM） |
| Claude Vision 判讀 prompt（含逐局累計驗算等對帳規則，踩很多坑換來的） | `index.html` / `submit/index.html` |
| 統計聚合邏輯（觀念可移植，程式要改寫） | `css/styles.css` |

**心理準備：現有前端當成「可執行的規格文件」，不是要移植的程式碼。**

### 後端：架構會反轉

現況是 `App → Cloudflare Functions（service role key）→ Supabase`，
安全完全靠那四個端點自己把關（而它們現在沒把關）。

新架構改成 **Supabase Auth + RLS**：
- 使用者用 **Sign in with Apple** 登入 → 拿到 JWT 與 `auth.users.id`（Scott 想要的 UUID 就是這個）。
- App 用 supabase-js 直接連 Supabase，**資料庫層** 用 RLS 政策擋住「只能讀寫自己所屬聯盟的資料」。
- **大部分 Cloudflare Functions 會消失**。
- **唯一必須留在伺服器端的是 Claude Vision 呼叫**（API key 絕不能包進 App），
  改成 Supabase Edge Function，驗證使用者 JWT 才執行，並加**每人每日解析配額**。

## 3. 資料階層（已定案）

```
聯盟 league          ← 哪一群朋友（1 人可加入多個）
 └─ 運動 sport       ← 聯盟建立時宣告要追蹤哪些（只玩棒球就不顯示 🏀）
     └─ 版本 title   ← MLB The Show 26 / 27、NBA 2K26…，有「目前使用中」旗標
         └─ 比賽 game
```

`games` 加 `league_id` + `title_id` 兩個欄位即可，**運動種類從 title 推導，不另存**。

### 為什麼運動在外層、版本在內層

- **跨運動的「全部」沒有意義**（安打不能跟籃板相加），所以生涯累積一定要有運動當範圍。
- **運動是永久的、版本會過期**。穩定的放外層、流動的放內層。

### 介面：不要做成兩排 tab

手機上兩排導覽吃太多高度，而且 95% 時間都在看當年度。

```
⚾ 棒球                       ← 頂部，沿用現有的 segmented control
  [ 生涯 ] [ 26 ] [ 27 ]      ← 下面一排小的，預設停在最新版本
```

**「生涯」＝該運動底下所有版本的累積，跟各版本並列在同一個選擇器裡**，
不是多一層導覽，只是版本選擇器的一個選項。

### 兩種統計範圍都要能看團隊數據與球員數據

Scott 特別想要的內容：**同一個球員跨版本的表現差異**
（「他某一年特別會用」），例如：

> **Scott 的 Aaron Judge**　26 年 .312 / 42 轟　→　27 年 .245 / 18 轟

這是這個 App 獨有的內容（一般戰績 App 只記勝負，這裡連個別球員 box score 都有），
朋友之間會互相吐槽，是很強的回訪誘因。

⚠️ **前提：球員名字正規化必須一開始就做。**
AI 可能讀成 `Aaron Judge` / `A. Judge` / `Aaron Judge Jr.`，資料庫會當成三個人，跨年統計直接破功。
解法：球員別名對照表，或寫入時模糊比對合併。**事後清髒資料很痛。**

### 新版本怎麼產生
聯盟設定裡有「目前版本」，上傳預設進去；核對畫面可改、也可在那裡新增版本。
**不要讓每次上傳都要選版本。**
（AI 分不出截圖是 26 還是 27，畫面幾乎一樣，只能靠使用者。）

## 4. 多聯盟的設計原則（已定案）

Scott 問「10 個會不會太多？評估點是什麼？」——從「希望長期使用」反推：

**上限不是瓶頸，真正的殺手是「聯盟安靜下來」。**
一個人不上傳 → 數據停在三週前 → 其他人打開沒新東西 → 一起不開了。通常兩三週就死。

用這角度看，**聯盟越多，每個越容易安靜**：在 10 個聯盟裡大概 8 個是死的，
主畫面變墳場；10 個聯盟的推播會吵到讓人關通知——通知一關，這個 App 就結束了。
實際上一個人「會固定一起打電動的朋友群」通常只有 1–3 個。

**結論與做法：**
- 上限設 **10**（當防呆，不當賣點），但**介面照 1–2 個活躍聯盟設計**，一個切換器就好。
- **不做聯盟探索／瀏覽**。這是私人小圈子工具，不是社群產品。
- **休眠機制**：30 天無新比賽的聯盟自動從主畫面收起。
- 真正該花力氣的是**降低上傳摩擦**（Share Extension）與**別人上傳時推播**。

## 5. Native 才做得到的功能（同時也是通過 Apple 4.2 的理由）

⚠️ Apple Guideline 4.2「最低功能要求」：純 WKWebView 包網站幾乎必被退件。
下面前三項是主要的「這不是網頁包殼」證明。

1. **推播通知** — fantasy 感的引擎，也是防止聯盟死亡的關鍵。
   「Alvin 剛上傳一場，你掉到第 2 名了」。iOS PWA 推播要加主畫面才有且不穩。
2. **Share Extension**（最適合這個 App 的一招）— 打完遊戲截圖後，
   iOS 分享選單直接出現這個 App，點一下就進解析流程。不用開 App、不用找相簿。PWA 完全做不到。
3. **Widget（WidgetKit）** — 聯盟排行放主畫面。「我現在第幾名」是最常想看的事。
4. **背景上傳** — 現在提交頁那句「請留在此畫面、不要離開」可以消失。
5. **Sign in with Apple** — 一鍵登入，不用密碼。
6. **相機直接拍**、**真正的離線瀏覽**（本機資料庫，不是不可靠的 SW 快取）。

### 上架還需要準備
- **隱私政策網址**（必填，目前沒有）
- **支援網址**（必填）
- 名稱**不得含 MLB / NBA / 2K / The Show**（商標，會被退件）

### 🔵 App 名稱（最優先，會影響 bundle ID 與 Supabase 專案名）

Scott 覺得「ESL」太直接，想要能呼應功能、有趣味的名字。候選（Claude 推薦順序）：

| 名稱 | 優點 | 缺點 |
|------|------|------|
| **Couch League（沙發聯盟）** ⭐ | 描述場景不是功能：朋友窩在沙發上打電動卻認真記戰績。有溫度、不限運動、中英文都成立 | 沒直接說「記錄」 |
| **Boxie** | 從 box score 來的暱稱，可愛好記，棒球籃球都通 | 不懂 box score 的人不知道在講什麼 |
| **StatSnap** | 直接點出「截圖變數據」，最容易被理解 | 工具感重，少了朋友的味道 |
| **Tally** | 極短好念，有「一筆一筆累積」的感覺 | 太通用，App Store 撞名機率高，要先查 |

Scott 原本想的 **BoxScorer**：不差，但唸起來卡；中文「計分員」很好，
但英文對應的 Scorekeeper 太通用。

## 7. 建議的開發順序（尚未與 Scott 確認）

1. **先補現況的洞**：delete-game 加驗證、submit-game 加限流、日期改台灣時區。
2. Supabase：新 schema（leagues / league_members / titles / profiles）＋ RLS 政策。
3. Expo 專案 scaffold ＋ Sign in with Apple ＋ 聯盟建立/加入。
4. 把現有畫面在 RN 重做（總覽／對戰／隊伍／球員）。
5. 上傳流程 ＋ Edge Function 解析（沿用現有 prompt）。
6. 推播 → Share Extension → Widget（Apple 4.2 的三張王牌）。
7. 隱私政策、支援頁、送審。
