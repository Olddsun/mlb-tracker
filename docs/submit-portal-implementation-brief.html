給 Claude Code 與 Codex 交叉驗證

ESL 戰績網站升級技術規格

最新決策：一次把架構整理乾淨。主站搬到 Cloudflare Pages，正式資料搬到 Supabase DB， 網站內直接提供「提交戰績紀錄」按鈕；Scott、Alvin、Vincent 輸入自己的簡單 token 後即可上傳 5 張 box score 截圖。 AI 解析與驗證通過後直接寫入正式資料，讓玩家打完後能立刻看到更新後戰績。

主站：Cloudflare Pages API：Cloudflare Pages Functions 正式資料：Supabase PostgreSQL 截圖：Supabase Storage AI：Vision + Structured JSON 流程：上傳後自動更新

核心方向

不再保留 GitHub Pages 當主站，也不再讓 data/games.json 當長期正式資料來源。 這次改版的目標是把 ESL 從「靜態資料展示頁」升級成「可提交、可查證、可擴充的聯盟紀錄系統」。

使用者體驗要保持極簡：選自己是誰、輸入 token、填誰用哪隊、上傳 5 張截圖。剩下由 AI 解析與後端驗證處理。

第一版不用做

  • 不用會員系統。
  • 不用 Scott 審核流程。
  • 不用 App Store。
  • 不用多聯盟。
  • 不用 NBA 2K schema。

針對 Claude 回饋的澄清

  • 確認步驟改成非阻擋：第一版不做上傳者確認，也不做 Scott 審核。AI 解析與驗證通過後直接寫入正式資料。
  • needsReview 不阻擋：若 AI 回傳 needsReview = true，只記錄在 submission log 與結果提示中，不阻擋寫入。這是打好玩的聯盟，速度優先。
  • 不再用 GitHub 當資料庫：新版正式資料是 Supabase PostgreSQL。GitHub 只保留程式碼，不再用 GitHub Contents API 寫 games.json。
  • 截圖不要塞進 Function body：第一版應採 Supabase signed upload URLs，前端直傳 Storage；Cloudflare Function 只處理 token、AI、驗證與 DB 寫入。
  • 重複提交偵測改成提示與紀錄：同日期、同兩位玩家、同隊伍、同比分高度相似時，記錄 duplicate warning，但第一版不阻擋提交。

玩家提交流程

1
玩家在主站點「提交戰績紀錄」。
2
選擇提交者：Scott、Alvin 或 Vincent。
3
輸入簡單 token。第一版 token 可暫時等於名字，例如 Alvin 輸入 Alvin。
4
填玩家隊伍對應，例如 Scott = Yankees、Vincent = Cubs。
5
系統取得 signed upload URLs，前端把 5 張截圖直傳 Supabase Storage。
6
AI 解析後，後端驗證資料一致性並偵測可能重複提交。
7
只要硬性驗證通過，就直接寫入正式 DB，並記錄這筆是誰上傳、是否有 AI / duplicate warning。

實作順序，避免一次爆炸

雖然目標是一次整理乾淨，但實作上要分階段交付。最重要的順序是： 先資料層遷移，再改前端資料來源，最後才做截圖上傳。

  1. 設計 Supabase schema。
  2. 把現有 data/games.json 的 8 場資料匯入 Supabase。
  3. 做 /api/games，回傳接近原本 games.json 的資料格式。
  4. 前端只把資料來源從 JSON 換成 API，UI 與統計先盡量不動。
  5. 驗證 DB 版首頁、隊伍、球員數據與舊版完全一致。
  6. 再做提交截圖、AI 解析、硬性驗證、寫入 DB。
  7. 最後把主站部署到 Cloudflare Pages。

不要照做的舊方案

  • 不要只建簡化版 games / batting_lines / pitching_lines，會漏資料。
  • 不要任何人知道網址就能提交，至少要有 player token。
  • 不要讓前端直接碰 Supabase service role key 或 AI API key。
  • 不要邊搬 DB、邊改 UI、邊做 AI 上傳又邊改統計邏輯。

Supabase Schema 草案

這份 schema 要完整保留現有 games.json 能呈現的資料：player of game、teamFull、line score、notes、打者位置、投手 record、HLD / SV 等 decision。 

create table players (
  id text primary key, -- scott | alvin | vincent
  display_name text not null
);

create table teams (
  id text primary key, -- yankees
  name text not null,  -- Yankees
  full_name text not null -- New York Yankees
);

create table games (
  id uuid primary key default gen_random_uuid(),
  legacy_id text unique, -- 2026-06-25-03，用於遷移與對照
  played_at date not null,
  sport text not null default 'mlb',
  winner_player_id text references players(id),
  player_of_game_name text,
  player_of_game_team text,
  submitted_by text references players(id),
  submission_id uuid,
  created_at timestamptz not null default now()
);

create table game_sides (
  id uuid primary key default gen_random_uuid(),
  game_id uuid references games(id) on delete cascade,
  player_id text references players(id),
  team_id text references teams(id),
  team_name text not null,
  team_full text not null,
  home_away text not null check (home_away in ('home', 'away')),
  runs integer not null,
  hits integer not null,
  errors integer not null,
  innings jsonb not null
);

create table batting_lines (
  id uuid primary key default gen_random_uuid(),
  game_side_id uuid references game_sides(id) on delete cascade,
  batting_order integer,
  name text not null,
  pos text,
  ab integer not null,
  r integer not null,
  h integer not null,
  rbi integer not null,
  bb integer not null,
  so integer not null,
  hr integer default 0
);

create table pitching_lines (
  id uuid primary key default gen_random_uuid(),
  game_side_id uuid references game_sides(id) on delete cascade,
  pitching_order integer,
  name text not null,
  decision text,
  record text,
  ip text not null,
  h integer not null,
  r integer not null,
  er integer not null,
  bb integer not null,
  so integer not null
);

create table game_notes (
  id uuid primary key default gen_random_uuid(),
  game_id uuid references games(id) on delete cascade,
  note_type text not null, -- hr | sb | error
  player_name text not null,
  count integer
);

create table submissions (
  id uuid primary key default gen_random_uuid(),
  submitted_by text references players(id),
  player_a text not null,
  team_a text not null,
  player_b text not null,
  team_b text not null,
  image_paths jsonb not null default '[]'::jsonb,
  parsed_game_json jsonb,
  status text not null default 'received'
    check (status in (
      'received',
      'uploaded',
      'parsing',
      'parsed',
      'committed',
      'failed'
    )),
  game_id uuid references games(id),
  needs_review boolean not null default false,
  uncertainties jsonb,
  duplicate_candidates jsonb,
  error_message text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

路徑用途

AI 解析要求

使用 Vision 模型搭配結構化 JSON 輸出。AI 不決定提交者身份，只解析比賽內容。

你是 MLB The Show box score 解析器。

使用者已提供玩家與隊伍對應，這些是事實，不可更改：
- Scott = Yankees
- Alvin = Dodgers

請從 5 張截圖判斷：
- 誰是主場 / 客場
- 最終比分、hits、errors
- 每局得分
- winner
- player of game
- 兩隊 batting lines
- 兩隊 pitching lines
- notes：HR、SB、errors

輸出必須符合後端定義的 JSON Schema。
如果欄位看不清楚，仍輸出最佳判斷，並標記 needsReview 與 uncertainties，不要編造。
needsReview 只作為警示紀錄，不阻擋提交。

提交後驗證

  • winner 必須與比分一致。
  • innings 加總必須等於 runs。
  • batting hits / runs 合計必須等於隊伍總計。
  • pitching runs allowed 必須等於對手 runs。
  • 投球局數必須是 9.0、7.1、0.2 這種棒球格式。
  • 驗證失敗時寫入 submissions.status = failed，不得寫入正式比賽表。
  • needsReview = true 時只記錄 submissions.needs_review = true 與 uncertainties，不阻擋正式寫入。

速度優先規則

  • 第一版不做確認畫面、不做人工審核。
  • AI 解析後，只要硬性驗證通過就寫入正式資料。
  • 成功畫面顯示：比分摘要、winner、player of game、是否有 needsReview 或 duplicate warning。
  • 若玩家事後發現錯誤，再由 Scott / Codex 後續修正資料。
  • 這個決策符合目前使用情境：朋友打好玩，打完立刻看戰績。

重複提交偵測

寫入正式 DB 前先查相似比賽，避免同一場被送兩次。

  • 同一天。
  • 同兩位玩家，不看順序。
  • 同兩支隊伍，不看順序。
  • 最終比分相同，或總分差距很小。
  • 若命中，寫入 duplicate_candidates 並在成功畫面提示可能重複。
  • 第一版不 hard block，也不要求二次確認。

資料遷移驗收

  • 現有 8 場資料全部匯入 Supabase。
  • DB 版 /api/games 回傳的資料足以讓現有 UI 正常渲染。
  • 首頁戰績、近期對戰、隊伍戰績、球員數據要與舊版一致。
  • 每一場 detail page 的 line score、batting、pitching、notes 都不能掉資料。
  • 遷移腳本可重跑，不能重複插入同一場 legacy game。

上線策略

  1. 先在 Cloudflare Pages preview 部署 DB 讀取版。
  2. 確認 UI 與舊 GitHub Pages 顯示一致。
  3. 再開啟提交頁與 upload / process API。
  4. 用一場測試資料驗證 signed upload、AI 解析、硬性驗證與 DB 寫入。
  5. 確認穩定後，通知三位玩家改用 Cloudflare 網址。
  6. GitHub Pages 可短期保留備援，但不再作為主站。
